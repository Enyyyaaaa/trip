社群截圖轉旅遊行程 Web App
GitHub Pages 前端互動原型規格書
版本： V1.0
開發方式： Vibe Coding
部署平台： GitHub Pages
技術限制： 原生 HTML、CSS、JavaScript
產品階段： 前端互動原型（Prototype）

1. 專案目標
開發一個互動式旅遊規劃網站，讓使用者體驗如何將 Instagram Reels、Threads 等社群平台的旅遊靈感整理成景點清單，再進一步規劃成每日行程。
此階段以驗證產品流程、介面設計及使用體驗為主，不追求完整的 AI 與後端功能。
網站必須能直接透過 GitHub Pages 部署，不需要 Node.js、資料庫或後端伺服器。
核心使用流程
1. 建立旅程並設定基本資料。
2. 上傳旅遊截圖，或使用預設示範資料。
3. 查看模擬 AI 辨識的景點結果。
4. 確認、編輯及整理景點。
5. 查看自動產生的示範行程。
6. 在地圖與時間軸介面調整景點。
7. 儲存修改並匯出行程。

2. 技術架構與限制
2.1 使用技術
- HTML5：頁面結構。
- CSS3：視覺設計、排版與響應式介面。
- Vanilla JavaScript：互動操作、資料處理與頁面狀態。
- localStorage：儲存使用者的旅程資料。
- GitHub Pages：靜態網站部署。
不使用 React、Vue、Next.js 或需要建置流程的前端框架。
如有必要，可使用不需要後端的 CDN 套件，但應優先採用原生技術，減少相依性。
2.2 專案檔案結構
建議使用以下結構：
travel-planner/
├── index.html
├── css/
│   └── style.css
├── js/
│   ├── app.js
│   ├── data.js
│   └── storage.js
├── assets/
│   ├── images/
│   └── icons/
└── README.md
各檔案職責：
- index.html：主要頁面結構。
- css/style.css：全站樣式與響應式排版。
- js/app.js：互動邏輯、頁面切換與事件處理。
- js/data.js：示範旅程、景點及行程資料。
- js/storage.js：本機儲存與讀取。
- assets/：圖片及圖示資源。
- README.md：專案說明與 GitHub Pages 部署步驟。
如果實際開發需要更簡單的結構，也可以調整，但必須保持 HTML、CSS、JavaScript 的職責清楚。

3. 視覺設計規範
3.1 整體風格
採用「旅行雜誌 × 現代生活風格」設計。
視覺關鍵字：
- 溫暖、自然、輕鬆。
- 留白充足。
- 卡片式資訊呈現。
- 柔和圓角。
- 清楚的資訊層級。
- 具有質感但不過度裝飾。
- 以圖片與景點資訊為主角。
避免傳統企業後台風格、過度鮮豔的漸層、密集表格，以及每個區塊都使用不同顏色。
3.2 建議色彩
用途色彩主背景#F7F5EF卡片背景#FFFFFF主色：森林綠#294D3B輔助色：鼠尾草綠#A9B9A2強調色：暖橘#D98655主要文字#292D29次要文字#777A72邊框#E7E4DA
以上為建議初始色彩，實作時應確保文字與背景有足夠對比。
3.3 字體與元件
- 使用系統字體，優先支援繁體中文。
- 按鈕、輸入框及卡片使用一致的圓角規則。
- 主要按鈕使用森林綠。
- 次要操作採用白底、細邊框或文字按鈕。
- 警告、錯誤及成功狀態需有清楚的文字提示，不只依靠顏色。
- 動畫應簡短且不影響操作。
3.4 響應式設計
- 桌面：地圖與時間軸並排。
- 平板：可調整兩欄比例或改為上下排列。
- 手機：改為單欄，透過頁籤切換地圖、行程及景點清單。
- 所有主要操作按鈕在小螢幕上仍須容易點擊。

4. 頁面與功能規格
4.1 首頁／旅程建立
首頁提供產品簡介、主要操作入口及旅程卡片。
功能：
- 顯示產品名稱及簡短介紹。
- 顯示已建立的旅程。
- 提供「建立新旅程」按鈕。
- 提供「載入示範旅程」功能。
- 顯示旅程名稱、日期、城市及景點數量。
- 支援開啟及刪除旅程。
建立旅程時，使用者可以輸入：
- 旅程名稱。
- 旅遊城市。
- 開始及結束日期。
- 主要交通方式。
- 旅遊偏好。
- 預算。
必填欄位應有驗證，日期範圍不合理時應提示使用者。
驗收標準： 使用者可以建立、開啟及刪除旅程，重新整理頁面後資料仍可保留。
4.2 截圖上傳與景點辨識頁
提供圖片上傳區，視覺上模擬社群旅遊內容整理流程。
功能：
- 支援選擇多張圖片。
- 支援拖曳圖片至上傳區。
- 顯示圖片預覽。
- 顯示已選圖片數量。
- 可以移除尚未處理的圖片。
- 提供「開始辨識」按鈕。
- 點擊後顯示模擬辨識中的狀態。
- 顯示預先設定的模擬辨識結果。
- 支援後續追加圖片及景點。
因為 GitHub Pages 沒有後端，第一版的「開始辨識」只會使用預先準備的示範資料，不得宣稱圖片已被真正的 AI 分析。
4.3 景點確認清單
每個景點以卡片顯示。
欄位包括：
- 景點名稱。
- 城市或地址。
- 景點圖片。
- 景點類型。
- 預估停留時間。
- 預估費用。
- 營業時間或待確認提示。
- 優先順序。
- 備註。
- 資料確認狀態。
操作功能：
- 確認景點。
- 編輯景點資訊。
- 刪除景點。
- 調整優先順序。
- 標記為備選景點。
- 手動新增景點。
- 處理疑似重複景點。
- 查看來源圖片。
模擬辨識結果需包含已確認及待確認項目，讓使用者能體驗不同狀態。
驗收標準： 使用者可以管理景點，且修改內容能反映在後續行程規劃頁。
4.4 行程規劃主畫面
這是整個產品的核心頁面。
桌面版分為三個主要區域：
1. 頂部旅程資訊與日期切換。
2. 地圖區域。
3. 每日行程時間軸。
建議地圖與時間軸採兩欄配置，並可依螢幕寬度調整比例。
頂部資訊
顯示：
- 旅程名稱。
- 旅遊日期。
- 當前日期。
- 已安排景點數量。
- 當日預算與總預算摘要。
地圖區域
第一版可以使用示意地圖、預設圖片或自製的靜態地圖視覺。
地圖必須呈現：
- 景點位置標記。
- 景點名稱或序號。
- 選取景點的突出效果。
- 與行程卡片的視覺對應。
若未串接真正的地圖服務，不得將示意路線或標記描述為真實地理位置與導航結果。
每日行程時間軸
每個行程項目應顯示：
- 開始與結束時間。
- 景點名稱。
- 預估停留時間。
- 預估交通時間。
- 費用。
- 鎖定狀態。
- 備註。
操作功能：
- 切換日期。
- 拖曳調整景點順序。
- 編輯景點時間。
- 編輯停留時間。
- 移除行程項目。
- 將景點加入或移出備選清單。
- 鎖定或解除鎖定景點與時間。
4.5 AI 行程建議面板
在行程頁提供 AI 建議面板，呈現模擬的行程最佳化結果。
可顯示：
- 建議調整景點順序。
- 可能的時間衝突。
- 行程過滿提示。
- 景點營業時間待確認。
- 預算超出提醒。
- 替代景點建議。
使用者可以選擇：
- 套用建議。
- 忽略建議。
- 保留原本安排。
此階段建議內容由 JavaScript 根據示範資料與簡單規則產生，不需呼叫真正的 AI API。

5. 互動規則
5.1 頁面切換
使用者可以在以下主要頁面切換：
- 我的旅程。
- 景點整理。
- 行程規劃。
可以使用導覽列、步驟導覽或其他清楚的介面，但不應讓使用者因為切換頁面而遺失未儲存的修改。
5.2 拖曳排序
行程卡片應支援拖曳排序。
完成拖曳後：
- 更新景點順序。
- 更新時間軸顯示。
- 儲存修改。
- 顯示必要的衝突提醒。
若瀏覽器或裝置不適合拖曳操作，仍須提供選單或按鈕作為替代方式。
5.3 時間編輯
修改開始時間、結束時間或停留時間後：
- 檢查時間格式。
- 檢查是否與其他活動重疊。
- 更新畫面。
- 顯示衝突警告。
- 儲存變更。
第一版不需要實作複雜的路線最佳化演算法，但基本時間衝突檢查必須真正運作。
5.4 鎖定功能
景點與時間可以分別鎖定。
鎖定只代表示範 AI 建議不能直接修改該項目，不代表使用者自己也不能編輯。
若使用者手動調整鎖定項目，可以先顯示確認提示，再依使用者操作更新鎖定狀態或內容。
5.5 自動儲存
旅程設定、景點清單及行程編輯都應在修改後儲存至 localStorage。
需處理：
- 首次使用。
- 已有資料。
- 儲存失敗。
- 資料格式不正確。
- 沒有可用的儲存空間。
畫面應顯示簡短的儲存狀態，例如「已儲存」或「儲存失敗」。

7. 本機儲存與資料限制
使用 localStorage 儲存旅程、景點與行程資料。
要求：
- 每趟旅程有唯一 ID。
- 不同旅程的資料分開管理。
- 頁面重新整理後能還原資料。
- 刪除旅程時清除相關資料。
- 初始化時若沒有資料，載入空白狀態或示範旅程。
- JSON 解析失敗時提供錯誤提示與安全處理。
圖片可以在當前頁面使用 URL.createObjectURL() 產生預覽，但此 URL 不應直接當作可永久保存的資料。
若要讓圖片重新開啟後仍存在，可在確認容量限制後採用 IndexedDB 保存圖片，或讓示範原型使用固定圖片資源。
本階段不做雲端同步、登入或完整備份還原。

8. GitHub Pages 部署
網站必須是可由靜態主機直接提供的檔案。
部署要求：
- 使用相對路徑引用 CSS、JavaScript 與圖片。
- 不依賴伺服器端 API。
- 不使用需要 Node.js 執行的功能。
- 不將 API 金鑰放入前端。
- 在 GitHub Pages 的專案子路徑下仍能正確載入資源。
- README 提供清楚的部署說明。
部署完成後，需測試：
- 首頁能正常開啟。
- CSS 與 JavaScript 正確載入。
- 主要互動按鈕可以操作。
- 旅程資料可以保存。
- 頁面重新整理後可以還原資料。
- 桌面與手機版面均可正常使用。

11. 給 Vibe Coding 工具的開發指令
請依照本規格書建立一個可部署至 GitHub Pages 的純前端旅遊規劃原型。
開發規則：
1. 僅使用 HTML、CSS 與原生 JavaScript。
2. 不需要後端、資料庫、登入系統或真正的 AI API。
3. 所有模擬功能都必須能透過前端互動展示。
4. 優先完成可操作的 UI，再逐步實作資料處理與本機儲存。
5. 不可只產生靜態截圖或沒有功能的按鈕。
6. 不得將模擬資料描述為真實查證結果。
7. 不得將 API 金鑰寫入前端。
8. 必須支援 GitHub Pages 的相對路徑。
9. 必須支援桌面與手機版面。
10. 每個開發階段都要列出修改檔案、完成項目與驗收結果。
請先完成 Phase 1 的頁面與視覺設計，確認整體介面後，再逐步實作互動、本機儲存與部署功能。
本專案的核心目標是先做出一個真正能操作的產品原型，而不是提前開發完整的 AI 旅遊平台。
